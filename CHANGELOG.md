# Changelog

## Unreleased

- Stage 0: project skeleton with solution (Core, App, Tests), tray icon with an "Exit" menu (English and German), CI workflow, MIT license.
- Stage 1: search core in `FileDetective.Core` without file system or database: `SearchNormalizer` (search form of names), `SearchQuery` (input parsing: quotes, `\`/`/` splitting, type filters, max. 8 terms, mode), `MemoryIndex` (16-byte entries in 65,536-entry blocks, 16 MiB name segments, `ReaderWriterLockSlim`, parallel matching with inherited folder masks, bounded best lists per thread, deterministic ranking, cancellation), `SearchEngine` with `IEntryResolver` (id to full path) and `IUsageLookup` (entries opened through the tool). Placeholder class removed.
- Measured (stage 1, Release build, AMD Ryzen 7 8745HS, 8 cores / 16 logical processors): search over 1 million generated entries, median per input, 4 threads: 5–14 ms for typical inputs, 14–30 ms for the worst case (single letter `e`, every entry is a hit); all 16 logical processors: 4–11 ms. Target under 50 ms on 4 cores is met. Debug builds are about 2–5x slower.
- Stage 2: database and storage in `FileDetective.Core`: `IndexDatabase` (SQLite schema from PLAN.md 6.1, `meta.schema_version`, WAL, `synchronous=NORMAL`; a file with a foreign schema version or a damaged file is renamed to `index.db.bak-<timestamp>` and recreated), `IndexStore` (only entry point for changes: entry numbers never reused and kept over restarts through `meta.max_id`, locations, batches written in one transaction and then applied to the `MemoryIndex`, subtree deletion, rename/move, removing a location, known children of a folder, loading the database into memory in one pass), `DatabaseEntryResolver` (`IEntryResolver`: entry number to full path and display data), `UsageTracker` (table `usage` keyed by path, `IUsageLookup` through a thread-safe map entry number to last opening). `MemoryIndex` got `UpdateMTime`.
- Measured (stage 2, Release build, AMD Ryzen 7 8745HS): loading 1 million entries from the database into the `MemoryIndex` takes 0.55-0.7 s (about 1.4-1.8 million entries per second); target under 3 s is met. Writing the 1 million entries in batches of 50,000 took about 8 s.
- Stage 3: scanning in `FileDetective.Core`: `RawEntry`, `IDirectoryLister` with `FileSystemDirectoryLister` (`FileSystemEnumerable`, `IgnoreInaccessible = false`, never a partial result), `ExcludeRules` (folder names, full paths with environment variables and `*` per path part, file name patterns, System attribute; default lists from PLAN.md 7.3), `ILinkDetector` with `ReparseTagLinkDetector` (reparse tag from the listing of the parent, no open of the folder, also on shares), `IScanClock` with `SystemScanClock`, `Scanner` (own stack, comparison with the known children, batches of 5,000 changes, no comparison below folders new in this scan, links recorded but not entered, subtree scan from a known folder, cancellation, scan state in `roots`, single-threaded and rejecting a parallel call), pause rule for network locations (normal and "very gentle"), `ScanStatistics`. A folder that cannot be listed keeps its known subtree unchanged; an unreachable location changes nothing. `IndexStore.GetEntry` added.
- Measured (stage 3, Release build, AMD Ryzen 7 8745HS, SSD, local, no pauses): user folder with default exclusions: 6,679 directories, 25,404 entries, first scan 1.2 s, second scan (comparison) 0.5 s. Whole drive `C:\` without exclusions: 117,428 directories, 661,513 entries, first scan 19.8 s, second scan 9.7 s (target from PLAN.md 6.5: 500,000 entries in under 3 minutes). The index was written to a temp folder and deleted afterwards.
- Stage 4: search bar. `FileDetective.Core`: `PathShortener` (folder path cut in the middle), `BarPlacement` (position on the monitor in device pixels), `SearchCoordinator` (30 ms debounce, cancels the previous search, delivers only the newest result), `ExistenceCheck` (a hit that is not found is only removed from the directory when its location and parent folder are readable), `BarState` (footer phase, Tab cycle). `FileDetective.App`: `IndexService` (start-up on a background thread: open database, load into memory, create the user folder as location, scan it once with the default exclusions, reload usage), tray icon with menu (Search, status line, Exit; left click opens the bar), global hotkey Alt+Space through `RegisterHotKey` with `MOD_NOREPEAT` on a message-only window (failure is reported as a balloon), `SearchBarWindow` and `SearchBarViewModel` (borderless, topmost, created once and then shown/hidden, placed on the monitor under the mouse pointer, foreground via `AttachThreadInput`, closes on Esc and focus loss, virtualized list with file type icon from `SHGetFileInfo` with `SHGFI_USEFILEATTRIBUTES`, all keys from PLAN.md 8.4, context menu, footer states, open/show in Explorer/copy path, `UsageTracker.RecordOpen` after opening), `NativeMethods` for all Win32 calls. Environment variable `FILEDETECTIVE_DATA_DIR` replaces the data folder (for tests). `--autostart` starts without showing the bar. Highlighting of matches and greying out of unreachable locations follow in stages 6/7. A minimal `filedetective.log` in the data folder is a stop-gap until `FileLog` (stage 7).
- Stage 5: locations and settings. `FileDetective.Core`: `DriveDiscovery` over `IDriveSource` (local, removable and connected network drives with letter and UNC path from `WNetGetConnection`; never reads sizes or opens anything on a share; labels only for local drives, with a time limit), `LocationRules` (normalizing, nesting rule at path boundaries, case-insensitive, drive letter and UNC of the same target count as one place, `Check` for adding), `SettingsService` and `AppSettings` (`settings.json` as in PLAN.md 8.5, missing file gives defaults, a damaged file is renamed, atomic write, unknown fields kept), `HotkeyGesture`, `AutostartManager` (HKCU Run value `"<exe>" --autostart`, the registry is the only truth), `SingleInstanceGuard` (named mutex and wake event per user and data folder), `IndexStore.CountEntriesByRoot`. `FileDetective.App`: first-run set-up (only at the very first start), settings window with Locations, Exclusions, General and About (hotkey recorder, autostart, language after restart, update check setting, network politeness passed to `ScannerOptions.Politeness`), tray menu with "Update now" and "Settings", a second start wakes the running instance and shows the bar, a refused hotkey shows a balloon and opens the settings at General. `IndexService` replaces the fixed user folder: all scan starts go through `StartScan` (one worker, one location after the other; stage 6 replaces its inside), removing a location cancels its scan, deletes its entries and reloads the usage map. "Rebuild directory" and the update check itself are left for stages 7 and 8.
- Stage 6: keeping the directory current. `FileDetective.Core`: `ScanQueue` (one whole-location scan at a time on one worker thread, local locations and removable drives before shares, one entry per location, a manual request upgrades a waiting scheduled one, a request for the running location is served by it except after a buffer overflow, cancellation of one location with blocking while it is removed, shutdown), `LocationLocks` (one lock per location, held by whole scans and by the watcher, so the two never compare and write the same location at the same time), `ScanExecutor` (lock, start time and `attempts_today`, `ScanRoot`), `RefreshScheduler` (local locations 60 s after start; shares and removable drives only if the last complete scan was on an earlier local calendar day and the location is reachable, checked 2 minutes after start, hourly and after a debounced network change; at most three automatic attempts per calendar day; "Update now" always runs and does not count; clock and reachability injected), `ReachabilityMonitor` (`Directory.Exists` on its own thread with a 5 s limit, a hanging probe is reused instead of starting another thread, cached state that never blocks, re-check on opening the bar after 60 s), `LocalWatcher` with `IChangeSource`/`FileSystemChangeSource` (only local locations, events collected per path for 300 ms, one worker, "reconcile path" against a complete listing of the parent, removal only after a successful listing, a vanished parent is decided by its own parent, new folders scanned as subtree, renames moved directly when both listings confirm them, exclusions, buffer overflow or watcher failure requests a full scan, events of never-scanned locations left to their first scan), `Debouncer`, `ScannerOptions.Progress`, `EntryDetails.RootId`, `ExistenceCheck` takes the known reachability (an unreachable location is not probed and never loses entries). `FileDetective.App`: `IndexService` rebuilt on these parts (watchers follow the location list, usage map reloaded at most every 2 s after watcher changes, `NetworkChange.NetworkAddressChanged` wired to the scheduler), tray status line and footer show the running scan with location and entries or "updated …", hits of unreachable locations are greyed out with "not connected" and only allow "Copy path", the location list shows "Not connected".
- Fix (found while reviewing the stage 3 wait path): `SystemScanClock.Pause` used `WaitHandle.WaitOne(TimeSpan)`, which cuts to whole milliseconds, so pauses below 1 ms after a fast share listing did not wait at all although the statistics counted them. The pause now waits at least the full measured duration (rounded up, repeated until it has passed). Test added.
- Measured (stage 6, Debug build, local temp folder): a new or deleted file is in the index 0.30-0.35 s after it was created or deleted (300 ms collection time included); a new file appears in the open search bar after about 0.4 s.
